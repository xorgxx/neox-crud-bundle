Configuration Reference (EN)

This document describes all options available under the neox_crud configuration key and their defaults. Override them in your config/packages/neox_crud.yaml.

Summary
- uploads_dir
- mercure.enabled
- mercure.topic_prefix
- makers.enabled
- makers.templates_namespace
- makers.base_layout
- translations.field_keys
- translations.patterns
 - Per-handler YAML overrides (index_fields)

---

Full overview (with defaults)

```yaml
# config/packages/neox_crud.yaml
neox_crud:
  uploads_dir: 'public/uploads'

  mercure:
    enabled: true
    topic_prefix: '/crud'

  makers:
    enabled: true
    templates_namespace: null
    base_layout: null

  translations:
    field_keys: ['label', 'placeholder']
    patterns: {}
```

Options details

1) uploads_dir
- Type: string
- Default: 'public/uploads'
- Description: Root directory for uploaded files, used by handlers/forms that need it. You can override it to point to another public dir or a mounted storage.

2) mercure
- Type: object
- Description: Real-time notifications via Mercure.

2.1) mercure.enabled
- Type: bool
- Default: true
- Effect: Enables/disables publishing CRUD events (create/update/delete) to Mercure via the default CrudNotifierInterface implementation.

2.2) mercure.topic_prefix
- Type: string
- Default: '/crud'
- Effect: Prefix applied to Mercure topics, for example `/crud/product/123`.

3) makers
- Type: object
- Description: Controls activation of the Maker commands provided by the bundle.

3.1) makers.enabled
- Type: bool
- Default: true
- Effect: If false, Maker commands `make:crud-handler` and `make:neox:crud` are removed from the command registry.

3.2) makers.templates_namespace
- Type: string|null
- Default: null
- Effect: Determines the base layout used by generated templates. It accepts either:
  - a Twig namespace (e.g. `Admin`, `NeoxCrud`) → the base layout becomes `@<namespace>/admin/_layout.html.twig`
  - a full Twig template path (e.g. `@Admin/Partial/_layout.html.twig` or `Admin/Partial/_layout.html.twig`) → used as-is
  Can be overridden per command via `--twig-namespace`.
  Note: final precedence for base layout also considers `makers.base_layout` and the CLI option `--twig-base-layout`.
  When everything is null/absent, generated templates fall back to `'/admin/_layout.html.twig'`.

3.3) makers.base_layout
- Type: string|null
- Default: null
- Effect: Explicit Twig base layout path to be used by the Maker when generating templates (e.g. `@App/admin/_layout.html.twig` or `/admin/_layout.html.twig`).
- Precedence: CLI `--twig-base-layout` > this `makers.base_layout` > `makers.templates_namespace` (derived to `@<ns>/admin/_layout.html.twig`) > default `'/admin/_layout.html.twig'`.

4) translations
- Type: object
- Description: Parameters for translation keys generated/used by forms and makers.

4.1) translations.field_keys
- Type: array<string>
- Default: ['label', 'placeholder']
- Effect: List of translation key suffixes generated by default for each field. Example for resource `product` and field `name`:
  - `product.field.name.label`
  - `product.field.name.placeholder`
- You may add 'help', 'hint', etc., if your templates support them.

4.2) translations.patterns
- Type: map<string, string>
- Default: {}
- Effect: Text templates used by the Maker to prefill some keys. Patterns can reference `%field_label%` (or other future variables) to interpolate a readable value.

5) Per-handler YAML overrides (index_fields)
- Type: file-based (optional)
- Default: not used
- Effect: Define which fields appear in the index view table for a given handler without overriding PHP code.

Location (first match wins), relative to your concrete handler class file (e.g. `src/Crud/Handler/ProductCrudHandler.php`):
- `src/Crud/Handler/ProductCrudHandler/config.yaml`
- `src/Crud/Handler/ProductCrudHandler/ProductCrudHandler.yaml`
 - `src/Crud/Handler/ProductCrudHandler/config/crud.yaml`

5.1) Per-handler UI actions (opt-in)
- Type: file-based (optional)
- Default: not used
- Effect: Configure action buttons for the index view without PHP changes. Fully backward compatible. If absent, templates render their defaults.

Supported optional keys in the handler YAML (flat or nested under `neox_crud:`):
- `actions`: per-row action buttons (index table column)
- `bulk_actions`: actions for the current selection (if your UI supports selection)
- `toolbar_buttons`: buttons displayed next to the "New" button in the index view

Action/button options:
- `name` (string, required)
- `label` (string; defaults to `name`)
- `icon` (string; optional icon class)
- `route` (string) or `path` (string)
- `method` (string; default `GET`)
- `confirm` (string; optional confirmation message)
- `class` (string; additional CSS classes)
- `priority` (int; higher first)
- `params` (map; supports dynamic placeholders)
- `voters` (string or list<string>; visibility/authorization handled by your Voter if you use one)
- `if` (string|bool; simple condition evaluated against `entity.*` or `context.*`)
- `selection_required` (bool; bulk only, default true)

Dynamic params and conditions
- You can reference entity and context values in `params` and `if` using:
  - `"entity.<prop>"` (e.g. `entity.id`, `entity.user.email`)
  - `"context.<key>"` (provided by the controller when resolving actions)
- The simple `if` evaluator supports truthy/!truthy checks, e.g. `entity.enabled`, `!entity.archived`.

Security
- Non-GET actions rendered by the starter templates are protected with CSRF tokens for the built-in routes:
  - Delete: token name `delete_{id}`
  - Custom POST actions: token name `custom_{resource}_{id}_{action}`
- Unknown non-GET targets are not auto-posted for security (rendered disabled by default); adapt your own templates if needed.

Ordering
- Entries are ordered by `priority` (desc), then by `name` (asc) for stability.

Examples (nested form)
```yaml
neox_crud:
  actions:
    - name: edit
      label: "Edit"
      route: "neox_crud_admin_crud_edit"
      params: { id: "entity.id" }
      priority: 100
    - name: delete
      label: "Delete"
      route: "neox_crud_admin_crud_delete"
      method: DELETE
      params: { id: "entity.id" }
      confirm: "Confirm deletion?"
      class: "btn-outline-danger"
      priority: 50
      if: "!entity.archived"

  bulk_actions:
    - name: bulk_delete
      label: "Delete selected"
      route: "neox_crud_admin_crud_custom"
      method: POST
      params: { action: "bulk_delete" }
      selection_required: true

  toolbar_buttons:
    - name: export_csv
      label: "Export CSV"
      route: "neox_crud_admin_crud_custom"
      method: GET
      params: { action: "export_csv" }
```

UI rendering note (bulk actions)
- The bundle does not render `bulk_actions` by default in the starter index template to preserve backward compatibility.
- You can either override your index template to add a selection column + POST forms, or generate your CRUD with the Maker flag `--with-bulk-ui` which scaffolds a variant of the index template including the bulk UI.

Append default actions (opt‑in)
-------------------------------

You can instruct the handler to append the default CRUD buttons (Edit/Delete) after your custom actions without overriding them and without creating duplicates. Enable the YAML option `append_default_actions` (flat or under `neox_crud:`):

Example (flat key):
```yaml
actions:
  - { name: view, label: "View", route: app_product_show, method: GET, params: { id: "entity.id" } }
append_default_actions: true
```

Example (nested under neox_crud):
```yaml
neox_crud:
  actions:
    - { name: view, label: "View", route: app_product_show, method: GET, params: { id: "entity.id" } }
  append_default_actions: true
```

Behavior:
- If your actions do not include `edit` and/or `delete`, they will be appended at the end with the bundle routes (`neox_crud_admin_crud_edit`, `neox_crud_admin_crud_delete`) and appropriate methods (GET/DELETE).
- If you already provided `edit` or `delete`, no duplicate is added.
- By default (option absent or `false`), nothing changes: only your configured actions are rendered.

Backward compatibility
- If those keys are absent, nothing changes in runtime templates or behavior.
- Public APIs and route names remain unchanged.

Accepted keys:
```yaml
# Either flat key
index_fields: ['id', 'name', 'createdAt']

# Or nested under neox_crud
neox_crud:
  index_fields: ['id', 'name', 'createdAt']
```

Notes:
- If no file is found (or the key is missing/invalid), the default behavior applies: all Doctrine fields except `id`.
- Fully backward compatible and opt-in.

Advanced attributes (optional)
------------------------------

You can attach attributes to each field to control how it’s rendered in the index view, or whether it’s visible depending on voters/roles. Three equivalent syntaxes are supported and they remain backward‑compatible with the simple list.

1) Simple list (BC):
```yaml
index_fields: ['title', 'email', 'enabled', 'createdAt']
```

2) List of maps with a `name` (or `field`) key:
```yaml
index_fields:
  - { name: 'title' }
  - { name: 'email', format: 'text' }
  - { name: 'enabled', boolean_icon: true }   # render ✓/✗ icons
  - { name: 'image', type: 'image', class: 'thumb-48' } # render <img>
  - { name: 'createdAt', format: 'Y-m-d H:i' } # date/datetime format
  - { name: 'roles', voters: ['ROLE_ADMIN'] }  # visible only if voter granted
```

3) Associative map: field name as key, options as value:
```yaml
index_fields:
  title: ~
  email: { format: 'text' }
  enabled: { boolean_icon: true }
  image: { type: 'image', class: 'thumb-48' }
  createdAt: { format: 'Y-m-d' }
  roles: { voters: ['ROLE_ADMIN', 'ROLE_MANAGER'] }
```

Currently recognized options (non‑exhaustive):
- `format`: string. For dates, any PHP date format (e.g. `Y-m-d`). For plain text, you may set `text`.
- `boolean_icon`: bool. If true, render a check/cross icon for booleans.
- `type`: string. For example `image` to suggest rendering an `<img>` using the field value as URL/path.
- `class`: string. Additional CSS class to apply (e.g. on an image tag).
- `voters` or `voter`: string|string[] of security attributes; the template/controller can leverage this to hide a field when not granted.

Note: The template contract is unchanged. Existing templates can continue to read `fields` (names only). If you adopt attributes, also read `field_options` from the controller context: an associative array keyed by field name → options.

Tip:
- When using the Maker commands, a commented `config.yaml` is generated next to your handler. It includes the list of detected Doctrine fields for your entity and a ready-to-uncomment `index_fields` line pre-filled with those fields for quick start.

Advanced example

```yaml
neox_crud:
  uploads_dir: 'public/media'
  mercure:
    enabled: true
    topic_prefix: '/realtime/crud'
  makers:
    enabled: true
    # You can put either a namespace or a full template path
    # templates_namespace: 'Admin'                      # namespace
    # templates_namespace: '@Admin/Partial/_layout.html.twig'  # full path
    # Or define an explicit base layout (overrides templates_namespace)
    # base_layout: '/admin/_layout.html.twig'
  translations:
    field_keys: ['label', 'placeholder', 'help']
    patterns:
      placeholder: 'Enter %field_label%'
      help: 'Help about %field_label%'
```

Default field type mapping (Maker)
---------------------------------

When generating a CRUD, the Maker guesses Symfony Form field types from Doctrine metadata:

- string → `TextType`
- text → `TextareaType`
- integer/smallint/bigint → `IntegerType`
- float/decimal → `NumberType`
- boolean → `CheckboxType` (nullable booleans are generated with `required=false`)
- date/date_immutable → `DateType`
- datetime/datetimetz/datetime_immutable → `DateTimeType`
- time/time_immutable → `TimeType`
- uuid/guid → `TextType`
- array/simple_array → `CollectionType` with:
  - `entry_type=TextType`, `allow_add=true`, `allow_delete=true`, `by_reference=false`, `empty_data=[]`
- json → by default `TextareaType` for raw JSON editing. If the PHP property is typed as `array` (or the field name is `roles`), the Maker uses `CollectionType` with the same options as above so empty submission yields `[]` and not `null`.

These are safe defaults only for generated code. You can freely edit the generated FormType to match your exact UX needs.
